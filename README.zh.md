# dsh-token-stats

DeepSeek Harness 的 Token 用量统计插件，挂在设置面板里作为一个独立页面。

它读取本机已有的持久会话日志，把你平时只能靠猜的数字算出来。

## 展示内容

| 区块 | 说明 |
|---|---|
| 看板 | 六个数字：累计用量、单日峰值（带日期）、今日用量、近 7 天、日均用量（按活跃天）、缓存读占总量比例 |
| 每日 | GitHub 贡献图式热力图，总以今天结尾：**固定 18 周**、26px 方格，在卡片里居中。窗口刻意不再由卡片宽度推导 —— 那会让版块在宽屏上膨胀、在窄卡片里把方格压小；卡片窄于这个版块时只把方格缩到刚好放下 18 列。颜色深浅是**连续**的（见下文）。尚未发生的日期保留虚线格 |
| 每周 | 每周一根柱，与每日网格是**同一个版块**：同样的窗口、列距、宽高，逐列对齐；每根柱在自己的列内两侧留白，所以相邻两周读起来是两根独立的柱子 |
| 趋势 | 每个模型一条平滑折线。横轴粒度随范围自适应：一个月内按天、半年内按周、两年内按月、更久按年 |
| 占比 | 环状图展示所选范围内各模型占比，配完整图例，中心显示该范围合计 |

**一个范围选择器同时驱动趋势图与占比图** —— 两者在同一张卡片内，作用域只声明一次。

指标切换器同时驱动热力图、趋势图和环图：

* **总量** —— 未缓存输入 + 输出 + 缓存读 + 缓存写，与提供方上报的 `totalTokens` 完全一致。
* **输入+输出** —— 不含缓存读的窄口径。热会话里缓存读占绝对多数（开发这台机器上是 98.8%），所以两个口径并列提供而不混合。
* 输入、输出、缓存读、缓存写 —— 最后一项只在本环境真的上报缓存写时才出现；当前挂载的 provider 都不上报。

所有展示数字按当前语言使用单位：中文为万 / 亿，英文为 K / M / B。

## 安装

```bash
dsh plugin --profile web add github:mathangler/dsh-token-stats
```

装完重启正在运行的 `dsh web` 进程。

补丁会往 profile 里插一行宿主半边。浏览器半边由 `package.json` 里的
`dsh.client.platform: web` 声明自动加载。开发与验证基于 DSH `0.1.5-rc.1`。

刷新会立即返回，并在后台重新扫描，这期间屏幕上保留原有数字。宿主的
`sessionQuery` 提供 `observeSession` 时，正在运行的会话通过该观测读取；不提供时
插件依然可用，只是改为整份读取会话日志。

要更新已安装的副本，必须先移除再安装 —— spec 不变时 pnpm 不会重新解析 git HEAD：

```bash
dsh plugin --profile web remove dsh-token-stats
dsh plugin --profile web add github:mathangler/dsh-token-stats
```

在网络受限的环境里 `github.com` 本身可能不可达，但**安装仍然可用**：
pnpm 是从 `codeload.github.com` 取 tarball 的，那是另一个主机。

## 数字是怎么来的

Harness 只把 token 用量记录在一种持久事件上：`assistant/message` 的 `data.usage`；
生产这条消息的 provider/model 就在同一事件的 `data.message.source`。也就是说，
一条 assistant 消息是唯一同时携带用量样本和归属路由的原子单位 —— 这就是折叠
按消息级而不是按 turn 级进行的原因。

* **尝试槽位**：一次计费尝试可能产生多条 `assistant/message` 样本。样本以
  `(turn, step, epoch)` 为键，`epoch` 在 `llm/retry-started` 和 `assistant/attempt`
  上递增；同一槽位内后到的样本替换先到的，因此重试会被再次计费，而流式样本不会
  被重复计数。
* **分叉会话**：带 seed 的会话日志把父会话的事件作为前缀包含在内。前缀长度
  `inheritedEventCount` 会被跳过，分叉永远不会被计两次。
* **天的边界**跟随本机本地时区。
* **排名**按总量排序；超过 8 个模型时，尾部会合并成一个「其他模型」分片而不是被丢弃。
* **已移除的会话继续计数**：从列表里消失的会话保留它最后一次已知的用量 —— 一个会
  因为清理历史而变小的「累计」数字毫无意义。脚注会显示这类会话的数量。把
  `retainSessions` 设为 `false` 则只统计仍在列表里的日志（此时总量会随删除而减少）。
* **读不了的会话不会被吞掉**：被读路径拒绝的日志会计入并在脚注的 hover 里给出原因 ——
  因为少读一个会话会让所有总量偏小。

平台自带的 `deriveTurnTokenUsage()` **不是**数据来源。它是 turn 级的，无法把用量
归到某个模型，而且任何包含 compaction 的 turn 都返回 `undefined`。在开发这台机器
上，它只统计到 294.7M token，而本插件的折叠统计到 340.2M —— 它悄悄丢掉了约 13%
的真实用量。因此它只作为测试里的交叉校验：在它能推导的每个 turn 上，本插件的折叠
必须四个桶全部完全一致。

## 颜色标尺

热力图以**当前视图内最忙的一天**为锚点，用幂律映射：
`不透明度 = 0.15 + 0.85 * (value / max) ** 0.45`。三种候选都在真实数据上量过：

| 当天用量 | 线性 | 对数 | **幂律 0.45** |
|---|---|---|---|
| 8,885 | 0.150 | 0.200 | 0.158 |
| 14,963,448 | 0.198 | 0.777 | 0.383 |
| 25,885,348 | 0.233 | 0.819 | 0.449 |
| 111,566,640 | 0.508 | 0.933 | 0.726 |
| 264,785,241 | 1.000 | 1.000 | 1.000 |

* **线性**让普通日子变得无法区分：15M 与 26M 只差 0.035。
* **对数**让忙碌的日子变得无法区分：111M 与 265M（相差 1.53 亿）只差 0.067，
  也就是看不出来 —— 它恰好压平了重度用户最关心的区间。
* **幂律 0.45** 两者都能分开：最忙两天差 0.274，普通两天差 0.065。

指数是命名常量 `INTENSITY_GAMMA`：调小则高位对比更强，调大则低位更可分。任何单一
标尺都有固有代价：出现极端离群值时，其余日子会被推向底部。

## 性能与缓存

刷新能拿平台自己的数字回答就绝不重读日志。七件事让一次扫描变便宜（都在真实语料上
实测：25 个会话、42MB）：

* **首先读平台的 `tokenUsage` 投影**：`dsh-token-meter` 注册了投影单元，
  `dsh-session-projection-cache` 在每个 turn 边界把它落盘检查点。也就是说**平台早就
  把每个会话的 provider 上报总量折叠并存好了**。读回来只是一次 Map 查表加一次 schema
  校验（用列表里的 header 做生命周期身份核对）—— 不 open、不 stat、不读日志。
* **只有在真能改变结果时才去算 marker**：平台唯一没记录的是「按天/按模型」的拆分，
  这也是读日志的唯一理由。当一个会话的平台总量与上次拆分所对账的那个总量相同时，
  这个拆分就被证明仍然有效，于是直接沿用 —— 不 `stat`、不 `observeSession`、不读日志。
  这对活跃会话最关键：对正在写入的 13MB 会话做一次 `observeSession` 本身就要 4.5 秒，
  而每次刷新都付这个代价，只为得出「什么都没变」。
* **拆分推导有预算**：冷语料要把每个会话都放上日历需要约 20 秒的日志读取，这不该让
  任何一次打开面板去等。一次扫描最多花 `SPLIT_BUDGET_MS`（1 秒）推导拆分，其余延后；
  被延后的会话仍然报告平台给的**精确总量**（挂在未归属模型、会话创建那天），下一次扫描
  读它的日志再替换。被延后的会话会记下自己的位置是**按哪一行平台记录**对账出来的，所以
  下一次扫描能认出它已经被对账过、不再重读 —— 正是这一点决定了「再按一次刷新」快不快，
  写错就会让同一批会话在每次刷新时永远重新排队重读。
* **已封闭会话走持久化 handle，而不是 `readSession`**：`sessionQuery.readSession` 返回的是
  **校验过的**快照 —— 它要重放整个日志来证明格式正确，这在恢复会话时是对的，在数每条
  assistant 消息的四个数字时纯属浪费。同一份语料实测：**`readSession` 29.9 秒，`handle.read()`
  约 3.3 秒**，总量完全一致。
* **用元数据判断变化，键在日志而不是文件**：已封闭会话的 marker 取
  `sessionPersistence.stat()` 的 `eventCount`；只有拿不到计数时才用 `sizeBytes` ——
  因为存储层重新压缩一个**没变**的日志也会改变字节数，按键在字节数会让每次刷新把每个
  大会话白读一遍。
* **格式迁移不再丢掉缓存总量**：投影缓存把记录绑定到会话的格式代，所以一次 harness 升级
  把已存日志从 v3 迁移到 v4 后，按精确代去查会**全部落空** —— 实测这一次迁移悄悄让
  25 个会话里的 4 个失去了缓存总量。现在会多读一档「上一代」的记录，因为格式代决定的是
  日志**怎么解码**，而不是它上报多少 token。
* **最后一次聚合结果和 rollup 一起落盘**：宿主刚重启后的第一次打开也能直接从磁盘作答；
  扫描还会在每个会话之间交还事件循环，命中的请求不用排在一整轮扫描后面。

在**插件自己的 handler** 上端到端实测（同一份语料）：

| | 优化前 | 现在 |
|---|---|---|
| 冷扫描（无 rollup、首次启动） | 31.4 秒 | **约 1.2 秒** |
| 重启（磁盘上有 rollup） | 31.4 秒 | **3 毫秒** |
| **再按一次刷新** | **4–5 秒** | **0.14–0.7 秒**，零日志读取 |
| 打开面板（聚合已缓存） | 66–83 毫秒 | **7–47 毫秒** |

这些数字**不是**近似平台：每个会话折叠出的桶都会与它的 `tokenUsage` 总量对账，25 个
会话加总后与平台的差值实测为 **0.000%**。

打开面板都是立即作答，来源依次是 60 秒聚合缓存、落盘的聚合结果，最后才是
`stale: true` 的旧数据 —— 后者会在响应**之后**才重扫，面板同时做有限次补拉并显示一个
安静的「刷新中…」提示。手动刷新走同样的路径。

面板在**挂载槽位的 ref 回调**里测量宽度（而不是放在 effect 里 —— 冷启动时槽位元素还不存在，
effect 早就跑过了），并把宽度记到模块作用域。两个视图由**同一套几何**生成 —— 相同的周数、
列距、宽度和高度 —— 槽位预留的就是这个版块本身，而且只在真的量到宽度之后才预留。

宿主侧在服务挂载后**立刻**做一次预热扫描，而不是等固定 10 秒：这样第一次打开面板时
聚合已经在内存里。没有轮询，也没有定时器。

## 隐私

全部计算都在本地、基于磁盘上已有的会话日志完成，没有任何数据离开本机。插件不添加
任何模型可见内容：没有提示词段落、没有工具、也没有自己的模型调用。

## 配置

宿主行接受可选配置：

```yaml
- id: token-stats
  name: dsh-token-stats
  config:
    maxModels: 8
    retainSessions: true
```
